slop_score · metric reference

how the numbers get made

slop_score computes every number from source with a hand-written AST analysis — no LLM judge, nothing subjective. This page walks through each metric in isolation: what it counts, the exact formula, and a worked example.

Orientation

Before the numbers

Four independent things get measured, and none of them roll up into one score:

Erosion is a trend line, not a grade. An erosion of 0.586 means nothing on its own — you have one codebase, not a comparison population, so what matters is the slope between snapshots (--history), not the altitude.

Clones, repeated literals, and import cycles come with evidence. Every one of them is reported with the actual file:line locations behind it, not just a count — a hit is something you can go open in an editor.

Scope is the whole tree, recursively. Every metric below is computed once, over every .py file found under the path you give it — nested sub-packages included — minus directories like tests/, vendor/, and build/ (see DEFAULT_EXCLUDES, overridable with --exclude).

Headline number

Erosion

The share of the codebase's total complexity mass that sits inside high-complexity functions — a slow-moving trend line, backed by the ranked list of functions actually driving it.

Every function gets a "mass": its cyclomatic complexity (from radon) times the square root of its length in source lines of code (SLOC: lines carrying code, not blanks, comments or docstrings), as in SlopCodeBench's Eq. 2. Erosion is the share of total mass held by functions with complexity over 10. Weighting by mass, not just counting functions, means one long, tangled function can dominate the number even in an otherwise clean codebase — which is the point: that function is genuinely where most of the risk lives.

mass(f) = complexity(f) × √SLOC(f) erosion = Σ mass(f) for f where complexity(f) > 10 ───────────────────────────────────────── Σ mass(f) for every function f

A worked example, four functions in one module:

FunctionCCSLOCMassHigh (CC>10)?
A4164 × 4 = 16—
B182518 × 5 = 90yes
C797 × 3 = 21—
D356435 × 8 = 280yes
total407

high mass = 90 + 280 = 370 → erosion = 370 / 407 = 0.909

reading it

Only 2 of the 4 functions (50%) cross the CC>10 line, but they hold 91% of the mass. A headcount-based erosion ("50% of functions are complex") would have understated the real concentration of risk. That's why the mass weighting exists.

Functions driving erosion

Every function B and D above — the ones actually composing the numerator — is kept, ranked by mass ÷ total mass descending, and printed as a table: qualified name, file:line, cyclomatic complexity, cognitive complexity, and its percentage share of the whole codebase's complexity mass. This is the actionable half of the metric — erosion tells you the codebase is eroding; this table tells you exactly which function to open first.

FUNCTIONS DRIVING EROSION function file:line CC COG mass% parse_config cfg.py:88 34 41 18.2 _handle_request server.py:212 22 19 11.4 validate_payload io.py:44 17 26 9.1

Cognitive complexity (via complexipy, optional dependency — install with slop_score[cognitive]) rides alongside cyclomatic on every row rather than feeding its own threshold into the erosion formula. The two correlate ~0.93, so cognitive earns its place on the residual: it catches deeply nested code that CC scores as simple (requests' Response.iter_content: CC 7, cognitive 29) and forgives flat dispatch that CC punishes. cog_gt_15 — a raw count of functions over SonarCloud's default cognitive threshold — is reported separately alongside cc_gt_10 / cc_gt_30, not folded into the ranking's sort order.

without complexipy

Cognitive complexity is optional. Without it installed, the offender table still prints — CC and mass% are unaffected — with a - in the COG column and a one-line note in the report pointing at pip install slop_score[cognitive].

With evidence

Clones

Duplicated code at two granularities — whole functions, and statement blocks inside otherwise-different functions — each reported with a file:line for every member.

Both detectors normalise the same way before hashing: local variable names and literals are erased (x, "foo" → V, C) so a renamed copy-paste still matches, but attribute names and the name of a directly-called function are kept intact — otherwise results.append(x) and results.update(x) both collapse to V.A(V) and collide on shape alone. Matching now requires the same operation, not just the same syntactic silhouette.

Whole-function clones

Two or more functions (methods included, under a scoped qualname so a method isn't a false clone of itself) whose bodies — 3+ statements, docstring excluded — hash identically after normalisation.

whole-function duplicates, 2 group(s): 2x parsing.py::clean_text search.py::normalize_query 3x api.py::Handler.get api.py::Handler.post api.py::Handler.delete

Block clones

A duplicated run of 3+ consecutive statements inside two otherwise-different functions — the common case whole-function matching misses entirely. A window of that size slides over every block in the module (function bodies, branches, loop bodies, except handlers); windows sharing a normalised hash are clones of each other. A bare run of module-level statements (an import block, top-level constants) is never windowed on its own — two files sharing the same standard-library imports were matching as "clones" before this exclusion.

duplicated statement blocks, 1 group(s): 3x parsing.py:40-42 parsing.py:88-90 search.py:12-14

clone_ratio is the number of code lines (SLOC) covered by any qualifying group — block clones occurring at 2+ distinct locations, plus every member of a whole-function clone — divided by total SLOC. Numerator and denominator count the same kind of line, so the ratio is bounded by 1 without clamping. A block clone lying entirely inside the members of one whole-function clone is not listed again as a block: it's a slice of a duplicate already reported whole.

clone_ratio = |clone SLOC| / SLOC
overlapping windows are merged first

Sliding a 3-statement window by 1 over a genuine 6-statement duplicate produces 4 overlapping windows for what is really ONE location. Before anything is counted, overlapping or adjacent windows in the same file are merged into a single span — without this, one real duplicate reported as "8x" instead of "2x", and worse, a block of merely similarly-shaped statements that was never copy-pasted anywhere else (four self.x = None lines in a row, say — they all normalise to the same statement, so window [0:3] and window [1:4] hash equal) could pass the "2+ occurrences" bar purely by overlapping itself. A clone now has to occur at 2+ locations after that merge — self-overlap alone no longer qualifies.

then coalesced across windows

A real 4-statement duplicate, seen through a 3-statement window, still produces TWO different hashes — stmts[0:3] and stmts[1:4] — each a legitimate 2-location group after the merge above, but describing overlapping SLICES of one clone, not two separate ones. A second pass merges any two groups that have the same number of locations and pair up, file-for-file, with a touching/overlapping location in the other — so what would have printed as two 3-line groups prints as one 4-line group instead.

tuning

Window size (--clone-window, default 3 consecutive statements) is the dominant lever on the block-clone count. A window of 2 matches any two-statement idiom and is meaningless noise; 3 is a defensible minimum clone size — treat it as calibrated, not derived, and re-check it against your own repo before trusting the absolute value.

Divergent clones

Only available with --history. Structural duplication on its own is mostly benign — it's clones that drift that cause bugs. This compares each snapshot to the one before it: functions that were byte-for-byte structural matches last time and aren't any more get flagged, because it means one copy was fixed (or broken) and the other one wasn't.

prev snapshot — identical

class CsvExporter:
    def validate(self, rows):
        if not rows:
            raise ValueError

class JsonExporter:
    def validate(self, rows):
        if not rows:
            raise ValueError

current — diverged

class CsvExporter:
    def validate(self, rows):
        if not rows:
            raise ValueError
        check_encoding(rows)   # added here

class JsonExporter:
    def validate(self, rows):
        if not rows:
            raise ValueError

With evidence

Repeated literals

Two related signals, both about hard-coded values that want to be shared constants: the same string repeated inside one file, and the same list of strings repeated anywhere in the repo.

Repeated string

The same non-trivial string literal (3–60 chars) appearing 4 or more times in one module.

hidden by default

This one is noisy in practice — short identifiers and format specifiers recur for perfectly ordinary reasons, not because they're slop. It's still computed and always in the -o JSON, but the printed report only shows it with --show-literals; without the flag you get a one-line count pointing at the JSON instead. Repeated column list (below) is the sharper signal and always prints.

flags

raise ValueError("invalid configuration")
...
raise ValueError("invalid configuration")
...
log.warning("invalid configuration")
...
print("invalid configuration")

prefers

INVALID_CONFIG = "invalid configuration"
raise ValueError(INVALID_CONFIG)
...
log.warning(INVALID_CONFIG)

Each qualifying literal is reported with its exact count and every line it appears on, scoped to one file at a time:

REPEATED LITERALS 2 literal(s) repeated 4+ times in one file 5x 'username' models.py:14, 22, 88, 140, 201 4x 'created_at' models.py:23, 89, 141, 202
not flagged

A literal used only as a subscript key — df["username"], df[["username", "email"]] — is excluded here. On data-heavy code this used to be most of what this rule flagged, and it's a weaker signal than the pattern below: a column name repeated by structural necessity isn't a message copy-pasted four times.

Repeated column list

The same list or tuple of 3+ string literals, verbatim, reused at 2+ locations anywhere in the repo (not scoped to one file) — the pattern a single subscript key like df["username"] is excluded from above, because a whole schema copy-pasted between two call sites is a stronger, more specific signal than any one of its column names recurring.

flags

# models.py
COLUMNS = ["id", "name", "email", "created_at"]

# reports.py
rows = conn.execute(
    "SELECT * FROM users",
    ["id", "name", "email", "created_at"],
)

prefers

# models.py
COLUMNS = ["id", "name", "email", "created_at"]

# reports.py
from models import COLUMNS
rows = conn.execute("SELECT * FROM users", COLUMNS)
REPEATED COLUMN LISTS 1 list(s) of 3+ literals reused 2+ times 2x ['id', 'name', 'email', 'created_at'] models.py:2 reports.py:6

With evidence

Import cycles

Strongly-connected components of the intra-repo import graph: modules that cannot be understood independently of each other.

Every module's import ... and from ... import ... statements build a dependency graph, with each import pointing at the most specific module it names (from pkg import mod is an edge to pkg.mod when that's a module, else to pkg/__init__.py). Module names come from each file's import root, so src/ layouts and script directories resolve exactly; an absolute import that could mean modules under two different roots is skipped rather than guessed. Cycles are found with Tarjan's strongly-connected- components algorithm, so a 5-module tangle is reported as one component instead of every sub-loop inside it separately. Imports that don't run when the module is imported are excluded from the graph: those under if TYPE_CHECKING:, inside a function body, or under if __name__ == "__main__":. The first two are the standard fixes for a cycle, so counting them would flag the fix as the defect. They're still counted separately (type_only_imports, deferred_imports). Each cycle is reported with one concrete loop through it, as evidence you can follow file by file.

flags

# posts/service.py
from posts.repository import save

# posts/repository.py
from posts.models import Post

# posts/models.py
from posts.service import notify

reported as

IMPORT CYCLES  3/40 modules (8%) tangled
  models -> service -> repository -> models

Trust this most

Movement

Only available with --history: how erosion actually moved between snapshots — the one signal with no static equivalent.

delta_erosion_pct = 100 × (erosion[t] − erosion[t-1]) / erosion[t-1]

Printed as one row per sampled commit — ref, date, erosion, dEros%, and the raw cc_gt_10 / cc_gt_30 counts for that snapshot — so a run of --history reads as a trend line, not a single altitude. Divergent clones (see clones) are computed the same way, between each consecutive pair of snapshots.

why history at all

A single snapshot's erosion is uninterpretable without a comparison population — you have one codebase, not a benchmark suite. The trend line sidesteps that: whether 0.586 is fine or not doesn't matter nearly as much as whether it was 0.4 three months ago.

Every number on this page also lands in the JSON written by -o out.json — including the full, untruncated offender, clone, and repeated-literal lists (the printed report caps each at a handful of rows for readability). Run slopscore --help for the full flag list.
